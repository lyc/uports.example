# Guile 3.0.10 port report

## Port shape

This port installs GNU Guile 3.0.10 as a shared runtime, command-line
interpreter, compiler tools, development headers, Scheme source modules, and
precompiled `.go` modules.  The main runtime artifacts are:

```text
bin/guile
bin/guild
lib/libguile-3.0.dylib
lib/guile/3.0/ccache
lib/guile/3.0/extensions/guile-readline.0.so
share/guile/3.0
include/guile/3.0
```

The default source path is the official Savannah Git repository pinned to the
`v3.0.10` tag.  Setting `USE_SCM=` selects the GNU release tarball instead.

The Darwin plist was generated from the completed stage tree.  It is kept
separate because shared-library names and potentially generated artifacts are
platform-sensitive.  A Linux plist was not fabricated from a Darwin build and
still needs to be generated by a native Linux stage.

## Dependencies and configure policy

Required libraries are declared explicitly: BDW-GC, libffi, GMP, readline,
and libunistring.  Libunistring itself must be built with GNU libiconv
support; Guile's configure script checks this and rejects an iconv-less build.
Readline is declared rather than allowing configure to consume an undeclared
host `/usr/local` installation.

The build tool dependency uses the repository's `devel/pkg-config` port and
sets its sysroot and `.pc` search directory explicitly.  This avoids relying on
the framework's currently mismatched `USES=pkgconfig` dependency on the absent
`devel/pkgconf` path.

`pkg-config` itself is selected from the build-host tools exported by the
project wrapper.  It must not be constructed from the compiler group's
`DESTDIR`: that directory contains target libraries and `.pc` metadata, not
host executables.  The target metadata search covers both `lib/pkgconfig` and
`lib64/pkgconfig`, which keeps Linux hosts with either library layout working
while retaining the Darwin `lib` layout.

LTO is disabled.  Clang accepted `-flto`, but Darwin's linker produced a large
set of unresolved Guile internal symbols while libtool assembled
`libguile-3.0`.  On arm64 Darwin, upstream's hidden-visibility flag causes the
same problem during the non-LTO partial-link path.  A Darwin-only trailing
`-fvisibility=default` keeps those internal symbols available through the
final shared-library link.

Darwin builds retain the framework's `DESTDIR` rpath while configuring and
compiling so executable feature probes and bootstrap tools can load declared
dependencies.  After the framework adds the installed-prefix rpath, the
port's `post-stage` hook removes the temporary `DESTDIR` rpath.  Staged Mach-O
inspection therefore shows `@rpath` dependency names and `/usr/local/lib` for
this build, with no workspace paths remaining.

Linux does not receive the framework's temporary Darwin rpath.  Configure and
build subprocesses instead receive a build-only `LD_LIBRARY_PATH` containing
the target root's `lib` and `lib64` directories.  This lets executable probes
and the self-bootstrap runtime find declared dependencies without recording a
build-root rpath in the installed ELF artifacts.

The staged `guile-3.0.pc` is replaced with a relocatable version whose prefix
is derived from `${pcfiledir}/../..`.  Its compiler and linker flags use that
derived prefix and library names, so the metadata contains no build-root or
`DESTDIR` paths.

## Bootstrap classification and build flow

This is a required self-bootstrap build.  Configure selects Guile's supplied
`64-bit-little-endian` prebuilt bootstrap set.  The freshly linked Guile then
compiles stage0 bytecode, stage1 recompiles the compiler and modules with the
normal optimizer, and stage2 produces the final optimized module cache.  The
port does not depend on a previously installed Guile.

The observed flow was:

```text
configure and dependency probes
compile and link libguile plus the guile executable
generate procedure documentation with the new runtime
compile stage0 Scheme modules
compile stage1 optimized modules
compile stage2 final modules
install and strip into the stage tree
```

## Runtime verification

The staged interpreter was run with its staged source, compiled-module,
extension, and library paths.  The following behavior was verified with exit
status zero:

```text
arithmetic evaluation                         => 42
(ice-9 match) module loading and matching     => 42
UTF-16LE conversion through (ice-9 iconv)     => 12-byte result
(system foreign) FFI procedure availability   => #t
(ice-9 readline) native extension loading     => #t
```

These checks exercise the real interpreter, compiled module cache, Unicode and
iconv path, libffi-facing module, and dynamically loaded readline extension;
they are stronger than a version-only smoke test.

### Testing a staged or target-root installation

Guile loads `ice-9/boot-9` before it processes the `-L` and `-C` command-line
options.  Consequently, those options cannot by themselves relocate Guile's
own source and compiled-module trees.  A target-root test must set
`GUILE_LOAD_PATH` and `GUILE_LOAD_COMPILED_PATH` in the environment so they are
available during pre-boot.  Set `GUILE_EXTENSIONS_PATH` similarly for native
extensions.

These overrides are only required while running from a staged or target-root
location such as `local/compiler/usr/local`.  This build is configured with
the final `PREFIX` `/usr/local`, so its built-in module paths and Darwin rpath
refer to that final location rather than to `DESTDIR`.  Once the package is
actually installed at `/usr/local`, it should run directly without
`GUILE_LOAD_PATH`, `GUILE_LOAD_COMPILED_PATH`, `GUILE_EXTENSIONS_PATH`, or
`DYLD_LIBRARY_PATH`:

```sh
/usr/local/bin/guile
```

If `/usr/local/bin` is not already in the shell's normal command search path,
only `PATH` needs to be adjusted:

```sh
export PATH=/usr/local/bin:$PATH
guile
```

The same principle applies to any other configured final prefix: a correctly
installed runtime should use that prefix's built-in paths.  `-L`, `-C`, and
the `GUILE_*` variables remain useful for additional application modules, but
they should not be necessary merely to start the installed interpreter.
Linux still needs native validation to confirm that its installed loader can
resolve the final-prefix libraries through RUNPATH, `ldconfig`, or the host's
loader configuration.

From the installed prefix in this repository's compiler target root, the
Darwin test environment is:

```sh
cd local/compiler/usr/local

export DYLD_LIBRARY_PATH="$PWD/lib"
export GUILE_LOAD_PATH="$PWD/share/guile/3.0"
export GUILE_LOAD_COMPILED_PATH="$PWD/lib/guile/3.0/ccache"
export GUILE_EXTENSIONS_PATH="$PWD/lib/guile/3.0/extensions"
```

On Linux, replace `DYLD_LIBRARY_PATH` with:

```sh
export LD_LIBRARY_PATH="$PWD/lib:$PWD/lib64"
```

The following commands exercise the installed runtime and its important
module-loading paths.  `--no-auto-compile` is optional; it prevents a test from
creating user-side compiled-module cache files.

```sh
./bin/guile --no-auto-compile \
  -c '(display (+ 20 22)) (newline)'

./bin/guile --no-auto-compile \
  -c '(use-modules (ice-9 match))
      (display (match (list 42) ((x) x)))
      (newline)'

./bin/guile --no-auto-compile \
  -c '(use-modules (ice-9 iconv) (rnrs bytevectors))
      (display
        (bytevector-length
          (string->bytevector "hello!" "UTF-16LE")))
      (newline)'

./bin/guile --no-auto-compile \
  -c '(use-modules (system foreign))
      (display (procedure? pointer->procedure))
      (newline)'

./bin/guile --no-auto-compile \
  -c '(use-modules (ice-9 readline))
      (display (procedure? readline))
      (newline)'
```

The expected outputs, in order, are `42`, `42`, `12`, `#t`, and `#t`.

After Guile has enough environment information to boot, `-L DIR` can prepend
an additional Scheme source-module directory and `-C DIR` can prepend an
additional compiled-module directory.  They are suitable for application
paths, for example:

```sh
./bin/guile -L /path/to/application/modules \
  -C /path/to/application/ccache application.scm
```

The `-x` option adds a recognized filename suffix; it does not replace
`GUILE_EXTENSIONS_PATH`.  Likewise, `DYLD_LIBRARY_PATH` and
`LD_LIBRARY_PATH` are operating-system loader settings and have no Guile
command-line equivalents.

---

Guile needs ice-9/boot-9 before it processes -L and -C. Therefore,
relocating Guile’s own installation requires GUILE_LOAD_PATH and
GUILE_LOAD_COMPILED_PATH in the environment.

From your current directory, use:

```sh
env \
  DYLD_LIBRARY_PATH=./lib \
  GUILE_LOAD_PATH=./share/guile/3.0 \
  GUILE_LOAD_COMPILED_PATH=./lib/guile/3.0/ccache \
  GUILE_EXTENSIONS_PATH=./lib/guile/3.0/extensions \
  ./bin/guile
```

  Runtime test:

```sh
env \
  DYLD_LIBRARY_PATH=./lib \
  GUILE_LOAD_PATH=./share/guile/3.0 \
```

## Platform and manifest notes

The validated platform is arm64 Darwin.  Darwin uses `.dylib` for libguile but
Guile retains `.so` for its loadable readline extension.  Linux is expected to
use ELF `.so` names and needs its own native plist generation and runtime run.

The manifest is sensitive to Guile version, effective ABI (`3.0`), generated
module set, documentation options, NLS availability, and optional extension
probes.  Dependency or configure-option changes should therefore be followed
by a fresh stage, plist diff, Mach-O/ELF inspection, and real module-loading
tests.
